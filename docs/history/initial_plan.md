## 3. 优先处理的问题

### A. 停止导航／建图可能连主钟一起停止

证据：

- `navigation/scripts/stop_navigation_all.py` 的 matches() 明确匹配 `/opt/livox-navigation-home-runtime/scripts/ptp_supervisor.py` 及其 ptp4l 子进程；默认停止会向匹配进程发 SIGINT。
- `navigation/stop.sh` 调用该 root 清理入口；`mapping/scripts/session.py` 结束清理 raw_time 时也调用同一入口。
- `ptp_master/nuc-ptp-master.service` 的 ExecStart 正是上述 supervisor，且只有 `Restart=on-failure`。
- supervisor 捕获 SIGINT/SIGTERM，正常结束并写入 `healthy=false, reason=stopped`；正常退出不会触发 on-failure 重启。
- 已隔离执行纯 matches() 函数，确认它对该服务的 ExecStart 返回 True，没有调用进程扫描或发信号。

结论：这是静态确认的启停冲突，实机表现待复现。应在现场模式切换前修复：纯底盘下将系统主钟从业务清理范围排除，同时正常清理 raw_time；同步更新部署时安装到 /opt 的 root 快照。验证“导航→停止→建图→保存→导航”全流程主钟持续健康。单改 Restart=always 仍可能造成时间源重启及融合故障，不能替代隔离清理范围。

未修复时的临时恢复办法：在底盘停稳、运动服务退出后执行 `sudo systemctl restart nuc-ptp-master`，等待健康恢复再启动下一条业务链。不要在运动中重启主钟。

### B. 新雷达不能只改 IP

导航和建图各自的 `programs/sensors/config/devices.json` 固定了原雷达 MAC：

- .84：`4c:43:f6:6e:53:16`
- .85：`88:29:85:9b:8c:a0`

两套 `prepare.py` 都会核验 MAC，不符即拒绝启动。换了雷达需要确认前左／后右身份并更新两套配置；安装位置不同还要重新核对外参。`deploy.sh --iface` 只处理网口名，不能自动完成雷达身份和外参适配。

### C. 手柄模式与自主模式的防撞能力不同

独立手柄未接入自主导航的雷达防撞链路。默认平移最大 1.5 m/s，初始一档 0.05 m/s；右摇杆旋转有独立上限 0.4 rad/s，降低平移上限不会同步降低旋转上限。无线手柄断联是否可靠停车也必须实测，不能仅凭 USB 接收器仍在线判健康。

首次建议显式将手柄平移上限设为 0.1 m/s，从一档开始；物理急停有人看守。自主导航另设低速调试上限，手柄的命令行限速不作用于 Nav2。

### D. 多点巡航需要任务层

至少需要：地图绑定、点位 x/y/yaw、点位顺序、停留时间、循环次数、当前点显示、开始／暂停／取消、状态超时和失败停止。

- 当前点明确成功并停稳后才进入下一点。
- 规划失败、定位丢失、CAN 故障、状态断流或用户取消时，停止推进路线；恢复后重新确认，不自动跳点或盲目续跑。
- 新建地图后重采巡航点，不沿用旧地图坐标。
- 包内 waypoint_follower 配置是 `stop_on_failure: false`。若选用 Nav2 原生多点接口，需明确改为失败停止并接通现有运动门禁；不能仅凭服务存在就视为巡航完成。
- 网页关闭后的任务行为必须明确。首版建议由 NUC 本地任务进程持有路线，网页负责发起／查看／取消，并验收断网时的预定行为。

## 5. 现场操作提要

以下路径均为正式部署后的路径，不是审阅副本。先确认实际硬件身份、服务归属和停车状态，再执行涉及运动的步骤。

### 部署与静态检查

按原部署说明，从原包解压，使用 pc 用户执行 `./deploy.sh --iface 实际网口名`；首次不加 `--autostart`。已部署机器先核对版本和备份，不直接使用 --force 覆盖。

```bash
ip -br addr
ip -details link show can0
ls -l /dev/input/js0
id pc
ping -c 3 192.168.16.84
ping -c 3 192.168.16.85
ip neigh show
systemctl status nuc-ptp-master --no-pager
cat /run/livox-ptp/health.json
```

PTP 需要 mode=software、port_state=MASTER、healthy=true，并且健康文件持续更新；单张旧 JSON 不代表仍健康。包内导航入口还会检查时间新鲜度。pc 新加入 input 组后，需要新登录会话／重启使组权限生效。

### 独立手柄

先退出其他运动控制入口和建图，再启动：

```bash
cd '/home/pc/rk3588 link'
./start_remote_control.sh --max-linear-speed 0.1 --initial-gear 1
```

松开所有输入后按 START；左摇杆／方向键平移、右摇杆旋转、LB 降档、RB 升档；START 可解除使能请求，双扳机退出请求停车。纯底盘模式下 X/Y 不控制升降。

按短距离顺序测：前→后→左→右→左右旋转→松杆→失能→退出。最终以车轮实际停稳及反馈为准。独立手柄关闭网页不会自动退出；从原入口正常停止。

### 新场地建图

先停止运动服务和独立手柄，再停止导航；确认主钟仍健康。建图入口自己启动专用手柄，不要再同时开独立手柄。

```bash
cd '/home/pc/rk3588 link'
./start_mapping.sh --target-speed 0.1 --max-seconds 900
```

按日志静止约 20 秒，提示允许运动后中立按 START；先覆盖小范围、回到起点停稳；输入 `e` 回车后再静止约 20 秒，等保存和分析完成。建图脚本部分日志仍写“RK3588从钟”，实际模式要看 health 和代码分支，不要因此去连接 RK。

随后 8870“建图与修图”→生成并打开修图→检查通路／障碍→导出→退出修图→确认运动与定位停止→切换新图→重新定位。新场地不要用旧图试发目标；先备份新图、原始录包和外参。

### 单点导航及巡航前置

```bash
cd '/home/pc/rk3588 link'
./nuc_web.sh start
./nuc.sh start
./nuc.sh status
```

打开 NUC 实际 IP 的 8870 页面；定位 ready、地图姿态核对后，再启动运动服务→连接协议终端→使能底盘→发送近处地图目标。网页地图画面主要供监看，不能假设点击画面就能录巡航点。

自主绕障使用 map_target。line_target 是直线轨迹跟随，不等价于自主规划绕障。多点任务需等任务层补齐后才进入循环验收。

## 6. 验收记录

- 手柄：四向／旋转符号、松杆停车时间与距离、失能、USB 拔出／无线断联、重新连接后是否需要重新使能。
- 同步：双雷达在线、PTP 健康、融合 normal；检查 ±5 ms 时间门禁及是否反复重启。
- 模式切换：手柄→建图→保存→导航→运动→停止→手柄，全程仅一套运动控制器持有底盘，PTP 不丢。
- 定位：重启后可恢复；沿路线不出现未处理的跳变或丢失；实际地图朝向正确。
- 巡航：3～5 个点、每点停留、循环次数和取消；规划失败不跳下一点；新地图不接受旧点位。
- 障碍：单点低速先测减速、停住和恢复；巡航遇阻后按任务状态决定恢复／取消，不把遥操作碰撞恢复逻辑直接当作自主巡航续跑保证。
- 重启：先正常停止运动再关机；验收完成后再配置开机自启。现有自启不等于开机自动使能或自动巡航。
- 日志：部署 `/home/pc/nuc_deploy_*.log`；导航 `navigation/logs/one_click/`；手柄 `remote control/logs/`；建图 `mapping/logs/` 与 `mapping/runs/`；运动 `RK3588con/logs/`；网页 `web_console/logs/`；主钟 `journalctl -u nuc-ptp-master`。

现场仍待补充：底盘是否已部署、雷达是否沿用原两颗、实际网口名、轮子和雷达安装是否与原机一致、手柄型号／模式。多点巡航暂按“到点停车、可设停留时间、有限圈数循环”作为本周首版。
