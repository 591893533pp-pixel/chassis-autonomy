# 双 MID360S 雷达标定操作手册

版本：2026-11-25。适用：本底盘、ROS 2 Jazzy、双 MID360S、目标 NUC `pc@10.23.2.190`。

工具在 NUC：`/home/pc/dual_lidar_calibration_20261125`。所有标定命令在 **SSH 登录后的 NUC 终端**执行。脚本不使能电机、不发送 CAN 指令、不自动修改导航/建图配置。采集时会启动雷达扫描和 IMU，结束后关闭本次驱动。

## 1. 标定究竟得到什么

### 1.1 本工具标定的是两台雷达之间的外参

得到六个自由度：

| 信息 | 含义 | 单位 |
|---|---|---|
| tx、ty、tz | 前左雷达光学坐标原点在后右雷达光学坐标系中的位置 | 米 |
| roll、pitch、yaw | 将前左雷达测量轴旋转到后右雷达测量轴的姿态 | 度 |
| 4×4 刚体变换矩阵 | 上述旋转和平移的完整表示，作为程序使用的权威结果 | 旋转无量纲、平移米 |
| 质量报告 | 不同位置解的一致性、独立验证误差、共同视野、几何是否退化 | 报告中注明 |

约定为列向量：`p_rear = R @ p_front + t`。输出矩阵名 `T_rear_right_from_front_left`。这里的“后右坐标轴”是雷达光学坐标轴，**并不等于车体前、左、上**。rpy 为 SciPy `Rotation.from_euler('xyz', ..., degrees=True)` 的约定，不能直接当作任意软件的欧拉角顺序使用；对接时优先使用矩阵。

实际效果：两台看见同一面墙、地面时，合并后的点云应重合，避免双墙、错层、重影。

### 1.2 导航还需要雷达与车体之间的外参

车体约定：X 向前、Y 向左、Z 向上。车头已通过手柄实测确认。墙角不会告诉程序车头在哪里、车体中心在哪里，也不能单独确定雷达相对轮组运动中心的平移。

本工具固定“后右雷达相对车体”的旧 CAD 估计，仅更新前左雷达相对它的位置与姿态。因此输出分为：

- `relative_transform.json`：两台雷达之间的相对结果。
- `body_candidate_NOT_DEPLOYED.json`：借用旧后右 CAD 锚点得到的车体外参候选；绝对车体外参仍未验收。

若需要完整的车体外参，应另行核对底盘模型的 `base_link` 原点、实测安装中心/高度、机械前向及安装角；必要时使用带独立运动参考的联合标定。测外壳中心不一定等于光学原点，应查对应型号的安装图。

本工具不标定雷达内部距离偏差，不标定 LiDAR–IMU 时间延迟/外参，也不做运动去畸变或轮径标定。PTP 是采集前提，不是几何标定的输出。

## 3. 墙角怎么选、底盘怎么摆

优先选择室内两面平整的哑光墙形成的墙角，附近地面平整。墙面不必绝对90°，但应明显不平行，且地面作为第三个方向。不要选玻璃墙、镜子、大片金属反光面、移动人群、植物密集处或只有一条长走廊的场景。

参考摆放：

```text
墙面一 ───────────────┐
                      │ 墙面二
      A ↗   B ↑       │
          C ↖         │
                      │
```

示意图只表示多个观察姿态，不规定底盘绝对朝向。关键是两台雷达的共同可见区域包含两面墙和地面，且车体没有把它们全部挡住。

1. 底盘与每面墙先保持约 **1.5–3 米**；工具拟合使用距离各雷达 **1–10 米**的点，太贴墙会把有用点裁掉。
2. 让车体斜对墙角，两台雷达都能看到墙和地面的一部分。不要仅把一台雷达朝向墙角，另一台完全被车体挡住。
3. 确保雷达安装牢固、透明罩清洁且未被遮挡。标定期间不要扶着雷达或碰安装座。
4. A、B 为训练位置，C 为独立验证位置。B 相对 A 建议平移 **0.5–1 米**并转向约 **20–40°**；C 再换一处位置或反方向转向，仍保留共同墙角/地面。
5. 每组开始前车停稳，摇杆回中，**退出遥控程序**；采集期间不要推车、转车或走入共同视野。每组约8秒预热＋30秒采集，再加保存/退出耗时。

不需要贴棋盘格，也不需要人为测量墙角度数。不要为了获得“好看的结果”把墙角强制当作90°；算法利用实际共同平面。

在当前电脑终端登录：

```bash
ssh -i /home/pc/.ssh/id_ed25519_chassis_nuc pc@10.23.2.190
```

之后在 NUC 终端执行：

```bash
cd /home/pc/dual_lidar_calibration_20261125
./calibrate.sh check
```

预检检查依赖、网口地址/链路、两台网络可达、NUC PTP 健康和时间新鲜度、冲突进程与端口。它不启动雷达，因此 **“预检通过”不代表雷达已经出点云**；设备身份、HMS、设备PTP、数据流在采集时检查。

若提示有遥控/雷达/融合进程，回到启动它的终端正常退出。不要同时开导航、建图或其他雷达驱动。

## 5. 具体操作：A、B、C 三组

本例会话名 `corner_20261125_01`。以后用新的日期和编号，避免混入上次数据。相对会话名保存在工具的 `sessions/` 下；每个采集标签禁止覆盖，旧数据始终保留。

### A：第一个静止位置

摆好底盘后执行：

```bash
./calibrate.sh capture corner_20261125_01 A --pose-note 'A：距两墙约2米，斜对墙角，底盘静止'
```

`--pose-note` 应按实际摆放填写。等待终端打印 **“采集通过”** 或 **“静止标定采集通过（保留历史同步告警）”**，命令返回提示符后才能移动。后者仅允许0x04050002历史提示且实时同步、数据完整性与IMU静止检查通过；拟合前还会检验点云静止性。若打印“采集未通过”，先查具体原因，不要直接部署数据。

### B：换位置，用于交叉拟合

A 完成后，移动车体约0.5–1米并转向20–40°，停稳、退出遥控，然后执行：

```bash
./calibrate.sh capture corner_20261125_01 B --pose-note 'B：相对A向左约0.6米，转向约30度，底盘静止'
```

### C：再换位置，用于独立验证

C 不参与候选参数的选择；它检验参数是否对新观察姿态也有效。停稳、退出遥控，然后执行：

```bash
./calibrate.sh capture corner_20261125_01 C --pose-note 'C：相对B后移约0.7米并改变朝向，底盘静止'
```

位置变化数值可为估计，用于记录；应填写实际动作，不要照抄不存在的动作。三个标签对应同一位置反复采集，不能代替独立场景验证。

### 需要手柄移位时

手柄开机不等于遥控程序已启动。下面是当前底盘已验证的**限速移位入口**，仅在每组采集已完全退出、场地允许移动时使用。它不是标定脚本的一部分，不会由标定脚本调用。

在 NUC 终端执行：

```bash
sudo -n /usr/local/sbin/rk3588-link-can can0
python3 /home/pc/dual_lidar_calibration_20261125/run_reposition.py --phase motion --seconds 900
```

确认输出中的 CAN 状态正常（`ERROR-ACTIVE` 是正常错误主动状态；`ERROR-WARNING`/`BUS-OFF` 应先处理），手柄摇杆回中，按 START 使能，再低速移位。限制为平移0.05m/s、旋转0.04rad/s，所以转向会比较慢。停车后回中，在遥控终端按 Ctrl+C 或同时扣下双扳机退出，等待清理完成、返回提示符，再采集。900秒（15分钟）到时也会自动退出。若出现失能失败或不能停车，按已验证的物理急停/断开电机电源，不要继续采集。

若无需动力即可按现场允许的方式移位，也可以手动移动；不要强拖仍锁紧的轮子，不要拉雷达和线束。整个过程保持两台安装关系不变。

## 6. 一条命令拟合和验证

三组都采集通过后：

```bash
./calibrate.sh fit corner_20261125_01 --train A B --validation C
```

如果重采了 A2，应将 `--train A B` 改成 `--train A2 B`。也可以增加独立验证组 D，再用 `--validation C D`。同一标签不能同时用于训练和验证，复制同一份点云会被拒绝。

脚本先检查每组前后半段是否出现明显位移/旋转、场景是否有足够的方向约束；再分别在 A、B 中使用三个初值拟合。候选选择仅依据训练组，C 不参与选择。输出到：

```text
sessions/corner_20261125_01/result/
├── report.json                         完整质量报告、阈值和拒绝原因
├── relative_transform.json             两台雷达间的4×4矩阵及位置/姿态
├── body_candidate_NOT_DEPLOYED.json     未部署的车体外参候选
└── validation_C.png                    C组初值/候选的俯视与侧视对比
```

结果目录已存在时拒绝覆盖；如需重新拟合，先将旧 `result` 重命名保留，例如 `mv sessions/corner_20261125_01/result sessions/corner_20261125_01/result_previous`。不要修改原始点云来追求通过。

## 7. 怎样判断能否采用

程序退出码：0=该步骤在注明范围内通过（可能带历史告警）；2=采集/拟合质量未通过；1=配置/环境/执行异常。读终端提示和对应 JSON 原因，不能只看有没有生成文件。

拟合状态：

| 状态 | 含义 | 后续动作 |
|---|---|---|
| `RELATIVE_CHECKS_PASS_REVIEW_REQUIRED` | 自动相对几何检查通过 | 查看独立验证图，核对墙/地面、尺寸及安装关系 |
| `REJECTED` | 一项或多项检查未通过 | 按 `reasons` 排查，再采集；不要部署 |

当前初始验收门限（工程起点，不是厂家精度承诺）：

- 独立验证的双向匹配平面 RMSE ≤ **2.5cm**，95%绝对残差 ≤ **5cm**。
- 双向每侧匹配平面点至少1500，共同点云10cm以内匹配比例每侧至少15%。
- 各场景/初值的解相对候选位置差 ≤ **1cm**，姿态差 ≤ **0.3°**。
- 几何信息矩阵归一化最小特征值 ≥0.015，用于拒绝单墙等方向约束不足的情况。
- 相对旧初值修正不得超过8°或15cm，超过时先核对设备对应和初始安装姿态。
- 前后半段估计位移 ≤1.5cm、旋转 ≤0.3°；这不是对所有场景运动的绝对检测保证。

图中蓝色为前左，橙色为后右。右列候选应让共同可见的墙面和地面贴合，不能有明显双层、斜叉。同一物体只被一台看见时，本来就只会有一种颜色；不能要求所有点完全重合。图为了易读借用旧车体估计坐标显示，不能据图认定车体绝对坐标已标定。

匹配点集合会随参数改变，残差只统计可匹配平面，不等于全点误差、全局定位误差或地图精度。场景改变、人走动、遮挡会影响结果。过门限但图明显不对，也不能采用。

### 采用结果前最后核对

本工具**不会自动改正式配置**，两个 `calibrated` 标志也保持 false。相对结果经独立场景和图像复核后，可按工程配置要求接入融合；绝对车体锚点确认后再决定完整 `calibrated` 标志。不能因为脚本跑完就把所有标志改成 true。

当前正式导航/建图仍有旧机器的 IP、MAC 和时间策略，需要一并适配。仅复制一个外参 JSON 并不能完成导航接入。集成时先备份，保持驱动内外参全零，仅在融合层做一次变换，并核对 `coordinate_revision`、自体滤波坐标及时间健康检查，最后实际看融合点云再建图。

## 8. 常见问题

| 现象 | 优先处理 |
|---|---|
| 能 ping，但没点云 | 查 `metadata.json`、`diagnostics.json` 和 `driver.log` 的状态、HMS、目的地址；网络可达不等于雷达正常 |
| 后右状态4，HMS 0x02100003/0x02160003 | 这两个码在本机曾出现，重启后恢复，根因未确认；保留日志、查官方说明及供电。不要反复重启掩盖故障 |
| PTP不通过 | 确认网口链路、`/run/livox-ptp/health.json` 新鲜且MASTER；采集还会检查每台设备偏差≤500000ns和包标志 |
| 共同平面点不足/退化 | 增加两台共同看见的两面墙与地面；移远一些，避开车体遮挡，不要靠近只有单墙的区域 |
| 不同位置算出的参数不一致 | 查支架松动、采集时移动车体/有人遮挡、初值错误或共同区域太少；重新摆位采集 |
| 采集期间断网/SSH中断 | 当前程序可能仍在远端清理；重新SSH后先check，不要立即再开一套驱动。观察进程与日志后正常退出 |
| 手柄不动 | 检查手柄是否待机、限时会话是否已退出、CAN状态；标定程序不负责启动遥控 |

### 0x04050002 同步历史告警的处理

Livox 官方中文 HMS 表对 `0x0405` 的定义是“时间同步曾经发生过异常”，不是仅凭持续上报就能认定当前一直失步。参考：https://livox-wiki-cn.readthedocs.io/zh_CN/latest/tutorials/new_product/mid360/hms_code_mid360.html 。

2026-11-25现场修正：仅 `0x04050002` 可作为静止几何标定的历史提示；设备工作状态、序列号、其他HMS、实时PTP偏差与新鲜度、点云/IMU完整性和时间戳、主钟检查、退出清理、静止性仍需通过。严格健康字段 `health_ok` 仍为false，静止资格单独记录于 `static_review`，不等于导航/PTP系统验收。

旧脚本若只因这个历史提示拒收，可复核已有数据，无需先重启或重采：

```bash
./calibrate.sh review-static corner_20261125_01 B
```

复核将逐条检查原始诊断、包同步记录、流统计及点云前后半段；不改原 `metadata.json`、原始点云或诊断，另存 `static_geometry_review.json`（包含证据文件哈希）。`fit` 会再次复核，不是信任一个手填的合格标志。复核不通过仍需排查/重采；原采集出现过任何其他错误均不豁免。

本次 B 已复核可用于静止标定。后续本会话使用 `--train A2 B --validation C`。B中告警复发的起因仍未查明，不能把本次静止采集资格用作运动导航放行依据。处理顺序：

1. 先检查 NUC 主钟健康，以及两台 `time_sync_type`、`time_offset`、时间戳连续性；保留报错时的数据。
2. 保持 NUC 和交换机供电、网线连接稳定，主钟成为MASTER后再等待约10–20秒。尽量单独重启雷达，避免连交换机一起断电后重新经历主钟选举。若供电不可分开，应重新等待主钟健康。
3. 若只剩0x04050002且实时检查合格，按上述静止复核流程继续，不必为了清告警反复重启。需要排查/清除设备状态时可在主钟稳定后单独重启一次，再验证数据。2026-11-25实测重启后A2无告警，但B再次出现历史码而实时同步合格，不能把重启当成根治。
4. 若告警在网络/主钟稳定后再次出现，停止反复重启，检查PTP报文连续性、主钟身份/版本、是否存在其他主钟、链路掉线及主机时钟跳变。需要抓取同步报文时另行取得相应系统权限；不要盲目改PTP间隔、关闭门控或手动跳改系统时间。

NUC显示NTP未同步，不等于雷达相对NUC的PTP失败；当前场景先保证本地时间连续和设备间一致。若需UTC绝对时间，应单独设计校时方案，避免采集中突然调整主时钟。

## 9. 保存和下次复用

每次用新的会话名，例如 `corner_20261201_01`，完整保留 A/B/C、metadata、diagnostics、driver.log 和 result；采集失败也保留日志。原始数据占用取决于场景，通常每组数十MB以内，留出至少1GB空间。

只更换NUC但雷达安装未动：可以先用旧相对参数做独立验证。拆装雷达、更换支架、位置变化、发生碰撞后应重新标定。更换设备时更新 `config/settings.json` 的IP和序列号，以及 `config/driver.json` 的IP/主机地址；保持驱动外参为零，并重新核对初值。本版按前左/后右固定角色编写，不是自动发现任意两台雷达的通用程序。

算法自检（不连接硬件）：

```bash
OPENBLAS_NUM_THREADS=2 python3 -m unittest discover -s tests -v
```

工具包含已知变换恢复、单平面退化等检查；这些测试不能替代现场 A/B/C 验收。
